# База клиентов и признаков

Этап 9. База отвечает на один вопрос: **совпадает ли найденный файл, мод или запись с чем-то известным, и насколько надёжно это совпадение**. Она не выносит решения о нарушении: результат — запись о совпадении с видом совпадения и источником, а уровень находки задают правила корреляции (`docs/CORRELATION.md`). Код: `src/XINSkan.Signatures`, данные: `database/`, инструмент: `tools/XINSkan.DbTool`.

## Каталог функций

ТЗ, раздел 10: «Названия функций использовать как поисковые признаки, а не как самостоятельное доказательство». Каталог — `features.json`, 97 функций:

- **79 из списка заказчика** — в его порядке и по его категориям (combat, movement, visual, world, player, misc);
- **18 добавлены по исследованию** — функции, которые есть минимум в четырёх проверенных проектах, но не названы в списке (Surround, HoleFiller, AutoTrap, NewChunks, AntiHunger, FastPlace, AirPlace, HighJump и др.).

У каждой функции: название, категория, написания (в том числе как в исходниках: `Killaura` у Wurst, `AutoPotion` для AutoPot), **сила признака**, статус, **проекты, где она есть** (проект, имя модуля, путь к файлу исходника), источники с коммитом и дата проверки.

**Как проверялось.** В исходниках семи проверенных клиентов (Wurst, Meteor Client, LiquidBounce, BleachHack, KAMI Blue, SalHack, 3arthh4ck) выписаны все модули из их папок модулей — 1 087 модулей. Функция `verified`, если модуль с её названием есть хотя бы в одном проекте. Не нашлись нигде пять функций списка — `FastBow`, `BHop`, `Regen`, `ArrayList`, `CustomKeybinds`; они остаются `user-list`.

**Сила признака.** 45 функций — `strong`: такое имя класса почти не встречается вне чит-клиентов (KillAura, Scaffold, XRay, NoFall, Nuker, InventoryMove, AutoCrystal, ESP-семейство). 52 — `weak`: имя значит и обычное (Timer и ArrayList — классы Java, Velocity — прокси-сервер, Speed, Fly, HUD, FreeCam и FullBright — есть легальные моды). Слабые признаки показываются, но в `MultipleFeatureMatch` не считаются.

**Где ищутся.** File Hunter и Корзина читают у JAR только **имена** классов (классы не загружаются и не исполняются) и оставляют те, у которых имя совпало с написанием из каталога (`Jar.FeatureClasses`, не больше 150). Имя приводится к ключу: без пакета, без префикса `Module` и суффиксов `Module`, `Hack`, `Feature`, `Cheat`, `Mod` — так `KillauraHack` (Wurst), `ModuleKillAura` (LiquidBounce), `KillAuraModule` (SalHack) и `KillAura` (Meteor) дают одно и то же. Не учитываются вложенные классы и пакеты JDK, Kotlin, Minecraft, загрузчиков и распространённых библиотек. Отдельно отмечается описатель серверного плагина (`plugin.yml`, `paper-plugin.yml`, `bungee.yml`, `velocity-plugin.json`).

**Правило совпадения:**

| Найдено в одном JAR | Вид |
| --- | --- |
| ≥ 3 разных сильных функций из ≥ 2 категорий, не серверный плагин | `MultipleFeatureMatch` |
| то же в серверном плагине; 2 сильных; 1 сильная и ≥ 2 слабых | `PossibleMatch` |
| меньше | нет совпадения |

Классы в пакетах `check`, `checks`, `detection`, `detections` пропускаются: античиты называют свои проверки так же, как читы (`ac/grim/.../checks/impl/combat/Reach`). В описании совпадения перечислены функции с категорией и силой, полные имена классов и проект, с модулями которого набор совпадает больше всего, — с оговоркой, что это сходство набора, а не опознание.

## Формат

```
database/
  manifest.json   версия, дата, SHA-256 каждого файла, журнал изменений
  clients.json    записи: id, name, kind, status, ambiguous, variants, ambiguousVariants, identifiers, sources, note
  aliases.json    исходные написания из списков заказчика
  hashes.json     SHA-256 файлов: sha256, clientId, fileName, version, size, source
  features.json   функции: id, name, category, variants, strength, status, list, projects, sources, note
  mojang.json     официальные клиенты Minecraft: id, type, releaseTime, versionJsonSha1, clientSha1, clientSize; источник
```

`mojang.json` — SHA-1 JAR клиента всех 922 версий из файлов версий Mojang (`docs/MINECRAFT_INTEGRITY.md`). Список без источника `https://piston-meta.mojang.com/` не используется; версии с неправильным хешем отбрасываются.

`kind`: `client`, `utility`, `dll`, `launcher`, `loader`, `tool`, `feature`, `generic`. Название лаунчера само по себе не нарушение: такие записи дают только справочное совпадение.

Файлы сверяются побайтно, поэтому `.gitattributes` запрещает git менять в `database/` окончания строк (иначе при выгрузке на Windows с `core.autocrlf` база перестаёт совпадать с манифестом — так CI и нашёл это в первый раз).

**Проверка при загрузке** (`SignatureDatabase.Load`). Сначала хеши файлов сверяются с манифестом — расхождение отклоняет всю базу. Затем каждая запись проверяется отдельно, и неправильная отбрасывается с причиной в `Problems`:

- `verified` без источника с адресом `https://`;
- признаки (`identifiers`) у записи, которая не `verified`;
- хеш без источника `https://` и даты проверки, хеш не SHA-256;
- повтор `id` или хеша, псевдоним на несуществующую запись;
- функция `verified` без проекта из проверенных записей или без источника с коммитом; проекты у непроверенной функции; функция «по исследованию» без подтверждения; написание, которое уже принадлежит другой функции.

## Виды совпадений

Статусы ТЗ, раздел 11 (`SignatureMatchKind`):

| Вид | Когда | Что значит |
| --- | --- | --- |
| `ExactHashMatch` | SHA-256 файла есть в `hashes.json` | это тот самый файл |
| `VerifiedComponentMatch` | идентификатор мода (`fabric.mod.json`, `mods.toml`, вложенные моды), пакет верхнего уровня JAR или класс `Main-Class`/`Premain-Class`/`Agent-Class` совпал с признаком **проверенной** записи; или файл данных клиента лежит в папке игры (`.minecraft`, `minecraft` у Prism, или папка, которую File Hunter опознал как папку игры) | в файле есть компонент проекта; клиент работал в этой папке игры |
| `MultipleFeatureMatch` | несколько сильных функций из разных категорий среди классов одного JAR (см. «Каталог функций») | набор функций чит-клиента, без опознания конкретного |
| `NameMatch` | однозначное написание из списка совпало с именем файла, мода, версии, экземпляра или полями PE; путь файла данных клиента вне папки игры | совпало только название |
| `PossibleMatch` | неоднозначное или короткое (< 4 букв) написание, **только** в контексте Minecraft (папка игры, мод, версия); или компонент записи, которая не `verified` | может быть совпадением случайно |
| `Unknown` | ничего не совпало | записи не создаётся |

Сравнение имён — после нормализации (нижний регистр, без пробелов, дефисов, точек, подчёркиваний и окончаний `.jar`/`.dll`/`.exe`) по целым словам: имя разбивается на слова по разделителям и границам `camelCase`, и сравниваются последовательности до трёх слов. Поэтому `Wurst-Client-v7.40.jar` совпадает с `Wurst`, а `C:\Users\p\Pictures\sky.png` с `Sky` — нет: слово неоднозначное, а файл не в папке игры. `tools.jar` из JDK и `ForceWare` от NVIDIA тоже не совпадают (тесты). Для одной записи и одной записи базы остаётся только самое сильное совпадение.

## Как совпадение становится находкой

Корреляция получает совпадения вместе с фактами (`CorrelationEngine.Run(facts, matches)`):

- `SIGNATURE_MATCH` — на каждую запись базы и объект (или отдельную запись). Уровень: Medium для `ExactHashMatch` и `VerifiedComponentMatch` проверенной записи (прямая идентификация, достаточно одного источника); Low для `NameMatch` и `MultipleFeatureMatch`; справочный (Informational) для лаунчеров, общих слов и `PossibleMatch`.
- `FEATURE_SET_LOADED` — JAR с `MultipleFeatureMatch` загружался или запускался по другому семейству источников: Medium. High невозможен — конкретный клиент не опознан.
- `KNOWN_CLIENT_ACTIVITY` — проверенная идентификация **и** след использования того же объекта из других семейств (запуск, загрузка, удаление, переименование, агент JVM). High — только если основание охватывает три независимых семейства; иначе Medium. Только здесь `VerifiedIdentification = true`.

Название из списка никогда не даёт High: требование ТЗ «не присваивать High только по одному косвенному признаку» проверяется в `Finding.Validate`.

## Обновления

Встроенная база — ресурс сборки. Обновление — папка `signatures` рядом с программой (или указанная `xinskan signatures <папка>`) с теми же файлами и `manifest.sig`:

```json
{ "keyId": "первые 16 hex SHA-256 открытого ключа", "signature": "ECDSA P-256 / SHA-256, IEEE P1363, base64" }
```

Обновление используется, только если: подпись проверена ключом из `TrustedKeys.Default`, хеши файлов совпали с подписанным манифестом, записи прошли проверку, а версия новее встроенной. Иначе используется встроенная база, а причина записывается в отчёт проверки. Подмена файла, подпись чужим ключом, откат на старую версию — отклоняются (тесты).

**Ключ владельца.** `TrustedKeys.Default` пуст: ключа в репозитории нет и быть не должно. Владелец создаёт ключ на своём компьютере и добавляет в код только открытую часть:

```
dotnet run --project tools/XINSkan.DbTool -- keygen C:\keys\xinskan-db.pem
# выведет строку для TrustedKeys.Default: ["<keyId>"] = "<SPKI base64>"
```

Закрытый ключ не кладётся в репозиторий, в CI и на проверяемые компьютеры. Пока ключа нет, внешние обновления не принимаются — база обновляется вместе с программой, а отказ от внешнего обновления записывается в отчёт. Ключ сознательно не создан при разработке: подпись что-то значит, только если закрытый ключ есть у одного владельца.

**Выпуск обновления:**

```
xinskan-db manifest database --version 2026.12.01.1 --change "Что изменилось"
xinskan-db check database
xinskan-db sign database --key C:\keys\xinskan-db.pem
xinskan-db verify database --public <SPKI base64>
```

## Что пишется в проверку

- В журнал аудита — чтение папки обновлений (`signature-database`).
- В базу проверки (схема 3, `docs/STORAGE.md`) — какая база использована: версия, происхождение (встроенная или обновление), SHA-256 манифеста, ключ, число записей, проверенных записей и хешей, отброшенные записи и причины отказа от обновления. У находок — вид совпадения и `ClientId`.
- `xinskan signatures [папка]` показывает, какую базу программа загрузит, и почему.
- Если база не загрузилась (даже встроенная), корреляция всё равно выполняется, без совпадений; в аудите — ошибка `signature-database`, в ограничениях — `SIG.UNAVAILABLE` (High в такой проверке невозможен).

## Чего ещё нет

- **Хеши других выпусков и проектов.** Есть только три последних выпуска на GitHub пяти проектов. Старые выпуски, сборки с сайтов проектов (Wurst, Meteor, LiquidBounce) и файлы из списка заказчика без открытого источника нужно добавлять тем же путём: файл из названного источника → SHA-256 → запись с адресом и датой → новая подписанная версия базы.
- **Обфусцированные клиенты.** Набор функций ищется по именам классов; если имена заменены (ProGuard, коммерческие клиенты), признаков функций нет — остаются хеш, имена файлов, файлы данных и следы запуска.
- Проверка записей списка, у которых нет открытого исходного кода: нужны образцы файлов от заказчика с указанием, откуда они.
