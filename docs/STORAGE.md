# Хранилище проверки

Каждая проверка — отдельная база SQLite `evidence.db` в собственной папке, созданной через `OutputSink`. Код: `src/XINSkan.Storage`.

## Принципы

- **Только добавление.** Триггеры прерывают любой `UPDATE` и `DELETE` в таблицах `Evidence`, `SourceCoverage`, `ModuleResults`, `ModuleErrors`, `Investigations`. Даже ошибка в коде XIN SKAN не может переписать собранное.
- **Фиксация после каждого модуля.** Записи буферизуются (по умолчанию 5 000) и пишутся транзакциями без принудительного сброса на диск; `CheckpointAsync` записывает всё накопленное вместе с результатом модуля в одной транзакции. После фиксации записи модуля переживают отмену, сбой следующего модуля или аварийное завершение.
- **Компромисс надёжности и скорости.** Фиксация модуля всегда с принудительным сбросом на диск (`synchronous=FULL`). Промежуточные пакеты, которые только ограничивают память, передаются ОС без принудительного сброса (`NORMAL`): аварийное завершение XIN SKAN ничего из них не теряет, а отключение питания посреди модуля может потерять его незафиксированную часть. Причина — замер в CI: при сбросе на диск каждого пакета 100 000 записей писались 158 с.
- **Ошибка записи не теряет данные молча.** Если транзакция не прошла (например, повтор `EvidenceId`), ничего частичного не фиксируется, записи остаются в буфере, а ошибка поднимается наверх: проверка не может утверждать, что сохранила то, чего не сохранила.
- **Все файлы на учёте.** База открывается в режиме журнала `PERSIST`; файл журнала `evidence.db-journal` заранее заявляется через `OutputSink`. SQLite не создаёт и не удаляет файлов в обход учёта, и манифест целостности перечисляет всё содержимое папки.
- **Чтение не меняет базу.** `InvestigationReader` открывает её в режиме только для чтения; тест сверяет хеш файла до и после чтения.
- **Резервная копия.** `BackupTo` пишет согласованную копию в новый файл папки проверки (без журнала).

## Таблицы

| Таблица | Содержание |
| --- | --- |
| `SchemaInfo` | Версия схемы (2) и время создания |
| `Investigations` | Заголовок проверки: ID, время начала, версия, оператор, компьютер, ОС, часовой пояс |
| `Evidence` | Свидетельства по схеме v1 (`docs/EVIDENCE_SCHEMA.md`); структурированные поля — JSON |
| `SourceCoverage` | Покрытие источников |
| `ModuleResults` | Результат каждого модуля: состояние, время, число записей, причина |
| `ModuleErrors` | Ошибки, не остановившие модуль |
| `FileEvents` (представление) | Свидетельства о файлах: Existed, Created, Modified, Renamed, Moved, Deleted, Accessed, Downloaded |
| `ExecutionEvents` (представление) | Свидетельства о запуске: Executed, ExecutedLikely, Loaded |
| `CorrelationRuns` | Схема 2: когда выполнена корреляция, сколько записей прочитано, объектов и находок, её ограничения |
| `CorrelatedObjects`, `ObjectMembers` | Схема 2: файл, описанный несколькими записями, и его записи (связь по ссылке MFT или пути) |
| `Findings`, `FindingMembers` | Схема 2: находки правил корреляции (`docs/CORRELATION.md`) и их записи-основания и записи-контекст |

Таблица ТЗ `Correlations` реализована в схеме 2 как четыре таблицы выше. Таблицы корреляции тоже только дополняются (триггеры), а пишутся одной транзакцией после всех модулей, когда записи, на которые они ссылаются, уже в базе (внешние ключи на `Evidence`). Базы схемы 1 читаются как есть: таблиц корреляции в них нет, и читатель так и сообщает. Таблицы `NetworkEvents`, `NetworkConnections`, `NetworkApplications`, `TrafficStatistics`, `CheatSignatures`, `FeatureSignatures`, `HashSignatures`, `Applications`, `Reports` появятся в миграциях соответствующих этапов. `AuditLog` хранится не в базе, а отдельным файлом с цепочкой хешей (`docs/SECURITY.md`), чтобы его целостность не зависела от базы.

## Индексы

Нормализованный путь, имя файла, пара (запись MFT, sequence), время события, модуль, SHA-256 объекта — ключи, по которым работает корреляция.
